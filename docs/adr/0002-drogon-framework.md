# ADR-0002: Drogon as the C++ HTTP framework

**Date:** 2026-05-29

## Context

Corvus requires a C++17/20 HTTP framework to serve the REST API gateway
(`/health`, `/ready`, `/v1/*`), apply pre-routing and pre-handling middleware
(rate limiting, request size enforcement, request ID injection, JWT and API key
authentication), and eventually support WebSocket connections for the event bus.

Key requirements for the framework:

- Async, non-blocking I/O with a configurable thread pool
- Pre-routing and pre-handling advice hooks for middleware layering
- Middleware must be able to short-circuit the request pipeline and return an
  early response
- Post-handling advice for response decoration (e.g. echoing request IDs)
- Custom error handler registration for consistent JSON error envelopes on
  Drogon-generated responses (404, 405, 413)
- Static route registration with parameterised path segments (`/{a}/{b}`)
- WebSocket support (for Epic 4 event streaming)
- Active maintenance and vcpkg availability

## Decision

**Drogon 1.9.x** is the HTTP framework for the C++ core.

Drogon is registered as a vcpkg dependency (`drogon` in `vcpkg.json`) and
consumed via CMake's `find_package(Drogon CONFIG REQUIRED)`. The application
entrypoint calls `drogon::app().run()` after registering all middleware and
routes.

Middleware is layered using three Drogon hooks, applied in this order:

1. `registerPreRoutingAdvice` - fires before route matching; used for request
   ID injection, request size limit (Content-Length check), and rate limiting.
2. `registerPreHandlingAdvice` - fires after route matching, before the handler;
   used for JWT and API key authentication.
3. `registerPostHandlingAdvice` - fires after the handler sends a response;
   used to echo the `X-Request-ID` header.

`setCustomErrorHandler` handles Drogon-generated error responses (404, 405,
413) to ensure they conform to the standard Corvus JSON envelope.

## Alternatives considered

**1. Crow**
Crow is a header-only framework with a minimal API. It lacks pre-routing and
pre-handling middleware hooks, making layered auth and rate limiting awkward.
No equivalent to Drogon's advice chain. Rejected.

**2. Pistache**
Pistache is synchronous and blocking per connection. Its maintenance has been
inconsistent, with extended periods without releases. No pre-routing hook.
Rejected.

**3. cpp-httplib**
Single-header, synchronous, no async support. Suitable for embedded tooling
but not for a production gateway under concurrent load. Rejected.

**4. Boost.Beast (raw)**
Beast provides HTTP primitives but not a framework - routing, middleware, and
request lifecycle management would all need to be built from scratch. High
implementation cost with no meaningful benefit over Drogon's already-built
abstractions. Rejected.

**5. uWebSockets**
Extremely fast, but the API is low-level and the middleware model requires
significant custom scaffolding. WebSocket support is first-class, but HTTP
routing ergonomics are poor. Reconsidered if Drogon's WebSocket throughput
becomes a bottleneck. Rejected for now.

## Consequences

- Drogon 1.9.x is pinned in `vcpkg.json` via a dated baseline to ensure
  reproducible builds.
- Advice hook ordering is significant: `registerPreRoutingAdvice` callbacks
  registered first fire first. Middleware registration order in `main.cpp` is
  therefore part of the observable contract.
- `registerPreHandlingAdvice` only fires for requests that match a registered
  route. Unmatched paths are handled via `setCustomErrorHandler`. Any
  middleware that must run for all paths (including unmatched) must use
  `registerPreRoutingAdvice`.
- `registerPostHandlingAdvice` does not fire for responses generated by
  `setCustomErrorHandler` or by `preHandlingAdvice` callbacks that short-circuit
  the chain. Those responses must set headers (e.g. `X-Request-ID`) manually.
- WebSocket support is deferred to Epic 4. Drogon's WebSocket API is available
  without additional dependencies.
